# ARCHI Sales API

სერვისები გარე სისტემისთვის:

1. დილის ეტაპის შეცვლა (Sales ფაიფლაინი)
2. დილზე მიბმული ბინის დაჯავშნა / გათავისუფლება
3. პროექტების სია
4. ერთეულების (ბინა, პარკინგი, კომერციული) სია სტატუსით და ფასით
5. ლიდის გაგზავნა CRM-ში (არსებული სერვისი, ცალკე მისამართით)

## როგორ გამოვიძახოთ

- მისამართი: `<WEBHOOK_URL>/<მეთოდი>.json` — მაგალითად `<WEBHOOK_URL>/archi.sales.deal.stage.json`
- მეთოდი: `POST`, სხეული JSON-ით (`Content-Type: application/json`). `GET` პარამეტრებითაც მუშაობს.
- `<WEBHOOK_URL>` საიდუმლო გასაღებს შეიცავს — არ გააზიაროთ და არ ჩაწეროთ კოდის საჯარო რეპოზიტორიაში.
- 1-ელ და მე-2 სერვისში პასუხი ყოველთვის HTTP 200-ია. შედეგი წერია `result.STATUS`-ში: `OK` ნიშნავს წარმატებას, სხვა მნიშვნელობა — მიზეზს, რატომ არ შესრულდა.
- 1-ელი და მე-2 სერვისი მუშაობს მხოლოდ Sales ფაიფლაინის დილებზე, რომლებიც „რეზერვაციის“ ჩათვლით ეტაპებზე დგას. შემდგომ ეტაპზე ან დახურულ დილზე პასუხია `DEAL_LOCKED`.
- ეს მისამართი ეხება 1–4 სერვისს. მე-5 (ლიდის გაგზავნა) ცალკე მისამართზეა — იხ. ბოლო თავი.

## 1. ეტაპის შეცვლა — `archi.sales.deal.stage`

დილი გადაჰყავს მითითებულ ეტაპზე. მუშაობს ისე, როგორც თანამშრომლის ხელით გადაყვანა: CRM-ის ყველა ავტომატიზაცია ეშვება (მათ შორის ბინის სტატუსის შეცვლა — „რეზერვაციაზე“ გადასვლისას ბინა იჯავშნება, უკან დაბრუნებისას თავისუფლდება).

| პარამეტრი | სავალდებულო | აღწერა |
|---|---|---|
| `ID` | კი | დილის ID |
| `STAGE_ID` | კი | ეტაპის კოდი ქვემოთ მოცემული სიიდან |

ნებადართული ეტაპები:

| `STAGE_ID` | ეტაპი |
|---|---|
| `NEW` | გასანაწილებელი |
| `PREPAYMENT_INVOICE` | ახალი |
| `7` | ვერ დავუკავშირდი |
| `8` | დაინტერესებული |
| `9` | რეზერვაცია/პირობების შეთანხმება |

მოთხოვნა:

```json
{ "ID": 1500000, "STAGE_ID": "9" }
```

პასუხი:

```json
{
  "result": {
    "STATUS": "OK",
    "ID": "1500000",
    "CHANGED": true,
    "PREVIOUS_STAGE_ID": "8",
    "REQUESTED_STAGE_ID": "9",
    "STAGE_ID": "9",
    "STAGE_NAME": "რეზერვაცია/პირობების შეთანხმება",
    "STAGE_KEPT": true,
    "PRODUCTS": [
      { "PRODUCT_ID": "3352223", "NAME": "12", "PRODUCT_STATUS": "reserved", "RESERVED_BY_THIS_DEAL": true }
    ]
  }
}
```

- `STAGE_ID` პასუხში არის დილის რეალური ეტაპი ავტომატიზაციის შემდეგ. თუ CRM-მა დილი უკან დააბრუნა (მაგალითად, ბინა სხვაზეა დაჯავშნილი და რეზერვაცია ვერ შედგა), `STAGE_KEPT` იქნება `false`.
- `PRODUCTS` ბრუნდება მხოლოდ მაშინ, როცა გადაყვანა „რეზერვაციას“ ეხება (მასზე ან მისგან).
- თუ დილი უკვე ამ ეტაპზეა, პასუხია `OK` და `CHANGED: false`.

| `STATUS` | მნიშვნელობა |
|---|---|
| `OK` | შესრულდა |
| `INVALID_ID` | `ID` არ არის დადებითი მთელი რიცხვი |
| `INVALID_STAGE` | `STAGE_ID` არ არის მითითებული |
| `STAGE_NOT_ALLOWED` | ეტაპი არ არის ნებადართულ სიაში (პასუხში ბრუნდება სია `ALLOWED_STAGES`) |
| `NOT_FOUND` | დილი არ არსებობს ან არ არის Sales ფაიფლაინში |
| `DEAL_LOCKED` | დილი „რეზერვაციის“ შემდგომ ეტაპზეა ან დახურულია (`CURRENT_STAGE_ID`) |
| `UPDATE_FAILED` | CRM-მა ცვლილება არ მიიღო; მიზეზი `MESSAGE`-შია (მაგ. სავალდებულო ველი ცარიელია) |
| `ERROR` | შიდა შეცდომა |

## 2. ბინის დაჯავშნა / გათავისუფლება — `archi.sales.product.status`

ცვლის დილზე მიბმული ერთი პროდუქტის (ბინის) სტატუსს: `reserved` (დაჯავშნილი) ან `free` (თავისუფალი). წესები იგივეა, რასაც CRM იყენებს ეტაპების შეცვლისას.

| პარამეტრი | სავალდებულო | აღწერა |
|---|---|---|
| `ID` | კი | დილის ID |
| `PRODUCT_ID` | კი | პროდუქტის ID; პროდუქტი ამ დილზე უნდა იყოს მიბმული |
| `STATUS` | კი | `reserved` ან `free` |

წესები:

- `reserved` — სრულდება, თუ ბინა თავისუფალია ან უკვე ამ დილზეა დაჯავშნილი. გაყიდულ, სხვა დილზე დაჯავშნილ ან გაყიდვაში არმყოფ ბინაზე პასუხია `PRODUCT_NOT_AVAILABLE`.
- `free` — სრულდება მხოლოდ მაშინ, თუ ბინა ამ დილზეა დაჯავშნილი. სხვის ჯავშანს ან გაყიდულ ბინას სერვისი არ ეხება (`NOT_RESERVED_BY_DEAL`).

მნიშვნელოვანია: CRM დილის ყოველ ცვლილებაზე ბინის სტატუსს ეტაპს უთანხმებს — „რეზერვაციაზე“ მყოფი დილის ბინა დაჯავშნილია, უფრო ადრეულ ეტაპზე — თავისუფალი. ამიტომ ჯავშნის სანდო გზაა დილის გადაყვანა „რეზერვაციაზე“ პირველი სერვისით. ამ სერვისით დასმული სტატუსი, რომელიც ეტაპს არ შეესაბამება, დილის შემდეგი ცვლილებისას შესწორდება.

მოთხოვნა:

```json
{ "ID": 1500000, "PRODUCT_ID": 3352223, "STATUS": "reserved" }
```

პასუხი:

```json
{
  "result": {
    "STATUS": "OK",
    "ID": "1500000",
    "PRODUCT_ID": "3352223",
    "NAME": "12",
    "PREVIOUS_PRODUCT_STATUS": "free",
    "PRODUCT_STATUS": "reserved",
    "CHANGED": true,
    "DEAL_STAGE_ID": "9"
  }
}
```

`PRODUCT_STATUS`-ის შესაძლო მნიშვნელობები: `free`, `reserved`, `sold`, `not_in_sale`, `no_price`.

| `STATUS` | მნიშვნელობა |
|---|---|
| `OK` | შესრულდა (`CHANGED: false`, თუ სტატუსი უკვე ასეთი იყო) |
| `INVALID_ID` | `ID` არ არის დადებითი მთელი რიცხვი |
| `INVALID_PRODUCT_ID` | `PRODUCT_ID` არ არის დადებითი მთელი რიცხვი |
| `INVALID_STATUS` | `STATUS` არ არის `reserved` ან `free` |
| `NOT_FOUND` | დილი არ არსებობს ან არ არის Sales ფაიფლაინში |
| `DEAL_LOCKED` | დილი „რეზერვაციის“ შემდგომ ეტაპზეა ან დახურულია |
| `PRODUCT_NOT_ON_DEAL` | პროდუქტი ამ დილზე არ არის მიბმული |
| `PRODUCT_NOT_AVAILABLE` | ბინის დაჯავშნა არ შეიძლება; მიმდინარე სტატუსი `PRODUCT_STATUS`-შია |
| `NOT_RESERVED_BY_DEAL` | ბინა ამ დილზე არ არის დაჯავშნილი, ამიტომ ვერ გათავისუფლდება |
| `ERROR` | შიდა შეცდომა |

## 3. პროექტების სია — `archi.sales.project.list`

აბრუნებს ყველა პროექტს (კორპუსს / ბლოკს) და თითოეულში ერთეულების რაოდენობას სტატუსების მიხედვით. პარამეტრები არ აქვს. პასუხი ქეშირდება 5 წუთით.

მოთხოვნა:

```json
{}
```

პასუხი:

```json
{
  "result": {
    "projects": [
      {
        "id": 605,
        "name": "არქი ნუცუბიძე 2B",
        "units": { "total": 229, "available": 229, "reserved": 0, "sold": 0, "not_in_sale": 0, "no_price": 0, "unknown": 0 }
      }
    ],
    "count": 102,
    "generated_at": "2026-11-27T10:00:00+04:00"
  }
}
```

`id` არის პროექტის ID, რომელიც გადაეცემა შემდეგ მეთოდს `project_id`-ად. ახალი პროექტი სიაში თვითონ ჩნდება, როცა CRM-ის კატალოგში ემატება.

## 4. ერთეულების სია — `archi.sales.unit.list`

აბრუნებს ერთეულებს (ბინა, პარკინგი, კომერციული ფართი) სტატუსით და ფასით. ყველა პარამეტრი არასავალდებულოა.

| პარამეტრი | აღწერა |
|---|---|
| `project_id` | პროექტის ID წინა მეთოდიდან. თუ არ არის მითითებული — ყველა პროექტი |
| `status` | ერთი ან რამდენიმე: `available`, `reserved`, `sold`, `not_in_sale`, `no_price` (მასივი ან მძიმით გამოყოფილი) |
| `type` | `apartment`, `parking`, `commercial`, `office`, `other` |
| `limit` | რამდენი ჩანაწერი დაბრუნდეს; ნაგულისხმევი 200, მაქსიმუმი 500 |
| `after_id` | გვერდებად წაკითხვისთვის: წინა პასუხის `next_after_id` |

მოთხოვნა:

```json
{ "project_id": 605, "status": ["available"], "type": "apartment", "limit": 200 }
```

პასუხი:

```json
{
  "result": {
    "units": [
      {
        "id": 6120743,
        "number": "1",
        "project_id": 605,
        "project_name": "არქი ნუცუბიძე 2B",
        "type": "apartment",
        "type_label": "ბინა",
        "floor": 2,
        "rooms": 2,
        "area_total_m2": 56,
        "area_inside_m2": 43,
        "area_summer_m2": 13,
        "entrance": null,
        "view": { "ka": "შიდა ეზო", "en": null, "ru": null },
        "status": "available",
        "price_usd": 88200,
        "price_per_m2_usd": 1575,
        "updated_at": "2026-11-26T19:50:05+04:00"
      }
    ],
    "count": 1,
    "next_after_id": null
  }
}
```

- ფასი აშშ დოლარშია. გაყიდულ ერთეულზე `price_usd` და `price_per_m2_usd` ყოველთვის `null`-ია.
- `id` არის პროდუქტის ID — იგივე, რაც მეორე სერვისის `PRODUCT_ID`.
- გვერდებად წაკითხვა: თუ `next_after_id` არ არის `null`, გაიმეორეთ მოთხოვნა იმავე პარამეტრებით და `after_id`-ში ჩასვით ეს მნიშვნელობა; გააგრძელეთ, სანამ `null` დაბრუნდება. მთლიანი ბაზა (დაახლ. 32 000 ერთეული) 500-იანი გვერდებით დაახლოებით 20 წამში იკითხება.
- ცვლილებების თვალყურისთვის გამოიყენეთ `updated_at`.

ამ ორ მეთოდში შეცდომა ბრუნდება სხვა ფორმით — HTTP კოდით და `error` ველით:

| HTTP | `error` | მნიშვნელობა |
|---|---|---|
| 404 | `NOT_FOUND` | ასეთი `project_id` არ არსებობს |
| 400 | `INVALID_STATUS` / `INVALID_TYPE` / `INVALID_PROJECT_ID` | პარამეტრის მნიშვნელობა არასწორია |

## მაგალითი (curl)

```bash
curl -X POST "<WEBHOOK_URL>/archi.sales.deal.stage.json" \
  -H "Content-Type: application/json" \
  -d '{"ID": 1500000, "STAGE_ID": "8"}'

curl -X POST "<WEBHOOK_URL>/archi.sales.unit.list.json" \
  -H "Content-Type: application/json" \
  -d '{"project_id": 605, "status": "available"}'
```

## 5. ლიდის გაგზავნა CRM-ში (არსებული სერვისი)

ეს სერვისი უკვე მუშაობს — ამით შემოდის archi.ge-ს ფორმებიდან ლიდი. ის ზემოთ აღწერილი webhook-ისგან დამოუკიდებელია და ცალკე მისამართი აქვს.

- მისამართი: `POST https://crm.archi.ge/rest/deal/addLandingDealNew.php`
- სხეული: JSON (`Content-Type: application/json`).
- რას აკეთებს: ქმნის ახალ დილს Sales ფაიფლაინის პირველ ეტაპზე („გასანაწილებელი“), წყაროთი „ინტერნეტი/ვებ გვერდი“, და უშვებს CRM-ის სტანდარტულ დამუშავებას (კონტაქტის მოძებნა ან შექმნა ნომრით, დუბლიკატების შერწყმა, გადანაწილება).

ძირითადი ველები:

| ველი | აღწერა |
|---|---|
| `name` | კლიენტის სახელი და გვარი |
| `phoneNumber` | ტელეფონი. ქართული ნომერი შეიძლება `5XXXXXXXX`, `995…` ან `+995…` ფორმით; უცხოური — ქვეყნის კოდით |
| `dialCode` | ქვეყნის სატელეფონო კოდი, მაგ. `+995` |
| `country` | ქვეყანა, მაგ. `Georgia` |
| `email` | ელფოსტა |
| `officeName` | სასურველი ოფისი (იხ. ქვემოთ) |
| `officeId` | ოფისის ID საიტის მხარეს |
| `comment` | კლიენტის კომენტარი |
| `purpose` | შეძენის მიზანი |
| `projectLocation` | სასურველი პროექტი / ლოკაცია |
| `desiredKVM` | სასურველი ფართი |
| `spaceSize` | ფართის ზომა |
| `company`, `position` | კომპანია და თანამდებობა (იურიდიული პირისთვის) |
| `pageLocation` | გვერდის მისამართი, საიდანაც ფორმა გაიგზავნა |

`officeName`-ის მნიშვნელობები, რომლებსაც CRM ცნობს: `ფილარმონიის ოფისი და გალერია`, `ისნის ჰოუმ ოფისი`, `გლდანის ჰოუმ ოფისი`, `თამარაშვილის ოფისი`, `ბათუმის ოფისი`. ნებისმიერი სხვა ტექსტი (მაგ. `ნებისმიერი ოფისი`) ითვლება „სულერთია“-დ.

აქციის და რეკლამის ველები:

| ველი | აღწერა |
|---|---|
| `promotionsName` | აქციის სახელი |
| `promotionsId` | აქციის ID |
| `promotionsType` | აქციის ტიპი, მაგ. `Promotion`, `Presale` |
| `presaleType` | პრისეილის ტიპი |
| `UTM` | UTM კოდი (CRM-ში რეგისტრირებული აქციის მოსაძებნად) |
| `Source`, `Medium`, `Campeing`, `Content`, `Chanel` | რეკლამის წყარო, არხი, კამპანია, კონტენტი, არხის ბმული |
| `CampingName`, `AdGroupName` | კამპანიის და რეკლამის ჯგუფის სახელი |
| `StartUrl` | პირველი გვერდი, რომელზეც მომხმარებელი შემოვიდა |
| `Created` | ფორმის შევსების დრო |
| `FirstName`, `LastName` | სახელი და გვარი ცალ-ცალკე |

ველების სახელები ზუსტად ასე იწერება (მათ შორის `Campeing`, `Chanel`, `CampingName`). არცერთი ველი არ მოწმდება სავალდებულოდ, მაგრამ `name` და `phoneNumber` გარეშე ლიდი უსარგებლოა.

მოთხოვნა:

```json
{
  "name": "გიორგი ბერიძე",
  "phoneNumber": "599123456",
  "dialCode": "+995",
  "country": "Georgia",
  "officeName": "ფილარმონიის ოფისი და გალერია",
  "comment": "მაინტერესებს 2-ოთახიანი",
  "pageLocation": "https://archi.ge/ka/promotion/example",
  "promotionsName": "მაგალითი აქცია",
  "promotionsType": "Promotion",
  "Source": "meta_ad"
}
```

პასუხი (HTTP ყოველთვის 200, შედეგი `status` ველშია):

```json
{ "status": 200, "added": [], "leadId": 1528020, "message": "OK" }
```

| `status` | მნიშვნელობა |
|---|---|
| `200` | ლიდი შეიქმნა; `leadId` არის დილის ID (ის შეიძლება გადაეცეს 1-ელ და მე-2 სერვისს `ID`-ად) |
| `400` | სხეული ცარიელია ან არ არის სწორი JSON |
| `405` | CRM-მა დილი ვერ შექმნა |

პასუხს ჩვეულებრივ 3–10 წამი სჭირდება, რადგან დილის შექმნისას CRM-ის პროცესები ეშვება — მოთხოვნის ლოდინის დრო (timeout) დააყენეთ მინიმუმ 30 წამზე.
